# Running Focus Simulator on Android

Capacitor is already set up in this project (`capacitor.config.json`,
`@capacitor/android` in `package.json`), so this is mostly installing Android's
toolchain once and then two commands each time.

The app itself needs nothing from Android — no network, no account, and no
permission it does not ask for out loud. It is the same `dist/index.html`
running in a system WebView, with its data in local storage on the phone.

Two things are the exception and both are opt-in: the notification a running
block posts, and app blocking. Both live in `native/focus-guard` and are
described at the bottom of this file.

---

## One-time setup

### 1. Install Android Studio

Download from <https://developer.android.com/studio> and run it. On first launch
accept the standard setup — it installs the Android SDK, platform tools and an
emulator image.

Then check three things are present under **Settings → Languages & Frameworks →
Android SDK**:

- **SDK Platforms:** Android 14 (API 34) or newer
- **SDK Tools:** *Android SDK Build-Tools*, *Android SDK Platform-Tools*,
  *Android Emulator*
- **SDK Tools → SDK Command-line Tools** — Gradle wants these and the installer
  does not always tick it

### 2. Install a JDK — and it has to be 17

Android Studio ships one (JetBrains Runtime) and its own Run button will use it.

**For anything from the terminal, that JDK is probably too new.** `android/` is
generated by Capacitor and its Gradle wrapper is pinned at 8.2.1, which cannot
run under a JDK newer than 20 — recent Android Studios bundle 21 or 25. What you
get is:

    BUG! exception in phase 'semantic analysis' in source unit '_BuildScript_'
    Unsupported class file major version 69

which names a settings file and looks like a broken project. It is the Java.

    winget install EclipseAdoptium.Temurin.17.JDK

`npm run phone` finds it on its own, and says exactly this if it cannot.

**Check `~/.jdks` before installing one.** IntelliJ and Android Studio put a JDK
they downloaded there, and this machine had a working 17
(`C:\Users\<you>\.jdks\jbr-17.0.14`) the whole time `npm run phone` was saying
to install one. It looks there now, and in `~/.gradle/jdks` too.

**Until 2026-09-15 `npm run phone` could not have found any JDK at all**, the
one it recommends included, for two reasons that hid each other. It asked each
JDK its version by running `java -version 2>&1` under
`$ErrorActionPreference = 'Stop'`; java prints that to stderr, Windows
PowerShell turns stderr from a native program into an error record, and the
record threw — so every JDK read as version 0. And had one been found, the
result went into `$jdk`, which PowerShell treats as the same variable as the
`[string]$Jdk` parameter, so it was stored as the text
"System.Collections.Hashtable" and JAVA_HOME was set to nothing. It reads the
JDK's `release` file now, and the result is `$java`.

### 3. Add the Android project

In the project folder:

```
npm install
npm run cap:add:android
```

That builds `dist/`, then creates an `android/` directory — a real Gradle project
with the web build copied inside it. It is generated, so you don't need to keep
it in version control; `npm run cap:add:android` makes it again.

## Each time you want to run it

```
npm run android
```

Which does two things: `npx cap sync` (rebuild `dist/`, copy it into the Android
project, update plugins) and `npx cap open android` (open that project in Android
Studio).

Then in Android Studio:

1. Wait for **Gradle sync** to finish — the progress bar at the bottom. First run
   downloads the Gradle distribution and takes a few minutes.
2. Pick a target in the device dropdown in the toolbar:
   - **A real phone:** enable *Developer options* (tap *Build number* seven times
     under *About phone*), turn on *USB debugging*, plug it in, accept the
     prompt on the phone. It appears in the dropdown by name.
   - **An emulator:** *Device Manager → Create device* → pick Pixel 7 → a system
     image with API 34 → Finish.
3. Press **Run** (the green ▶, or Shift+F10).

It installs and launches. Editing the app afterwards means running
`npm run cap:sync` again and pressing Run — Capacitor copies the new `dist/` in;
Android Studio alone will keep building the old one.

## Porting an update to the phone, every time

```
npm run phone
```

Five steps in order, and the reason to have a script for it is that the one
people skip does not fail:

1. `npm run build` — `src/` into `dist/index.html`
2. `npx cap add android` if there is no `android/` yet
3. **`npx cap sync android`** — copies `dist/` into the native project and
   wires up any plugin that has been added
4. `gradlew :app:assembleDebug`
5. `adb install -r` and launch

**Step 3 is the one.** Skip it and everything still works: Gradle compiles
happily, the APK installs, the app opens — running last week's `index.html`.
The change looks like it did nothing. It is the same trap as launching the
desktop app from the Start menu instead of `start.cmd` (HANDOFF §4), and it
costs the same afternoon. **Check the build stamp at the bottom of the menu
against `package.json` whenever a change appears to have done nothing.**

`-r` on the install is load-bearing too: without it every install is a fresh
app with an empty calendar.

Other ways in:

| | |
|---|---|
| `npm run phone -- -ApkOnly` | build the APK, print the path, stop. For handing to somebody. |
| `npm run phone -- -NoLaunch` | install but do not open it |
| `npm run phone -- -SkipBuild` | native-only change; `dist/` and the sync are already done |
| `npm run phone -- -Jdk "C:\...\jdk-17"` | when it cannot find a usable Java |
| `npm run android` | the old route: sync, then open Android Studio and press Run |

A phone needs *Developer options* on (tap **Build number** seven times under
**About phone**), then **USB debugging**, then accept the prompt when you plug
it in. `adb devices` should list it as `device` rather than `unauthorized`.

If the install fails with a signature clash, a build signed with a different
debug key is already there. Uninstalling fixes it and throws away everything on
the phone, so **export a backup from the menu first**:

```
adb uninstall app.focussimulator.mobile
```

## Updates on the phone — what actually happens

Three different things get confused here, so, plainly:

- **The desktop app updates itself.** `electron-updater` downloads the new
  installer in the background and puts it in at the next ordinary exit. Nobody
  visits GitHub.
- **The phone app cannot.** A web view cannot replace the assets it was
  installed with, any more than a copied `index.html` can overwrite itself. So
  the in-app notice is a *link* — that is why **Get update** always takes you to
  GitHub. It is not a bug; it is the only thing that code can do.
- **The phone was not even noticing.** That one *was* a bug. A Capacitor web view
  has an origin of its own, so fetching `latest.json` from GitHub is
  cross-origin, and GitHub redirects release downloads to a host that does not
  allow it. The request was refused before it left the device and the app quietly
  concluded there was no news. Fixed by `CapacitorHttp.enabled` in
  `capacitor.config.json`, which sends that fetch through the native HTTP stack
  where CORS does not apply. Re-run `npx cap sync` after pulling this.

If you want the phone to genuinely update itself, pick one:

| Route | What it costs |
|---|---|
| **Play Store** (or any store) | A developer account and a review; the store then updates everybody. The normal answer. |
| **Live updates** — `npm install @capgo/capacitor-updater` | Swaps the *web bundle* at runtime, so everything in `dist/` updates without reinstalling. Native code changes still need a new APK. |
| **Hand over a new APK** | Free, and what you are doing now. |

## Building an APK to hand to somebody

**Debug** (fine for yourself and for testing, not for a store):

```
cd android
./gradlew assembleDebug          # Windows: gradlew.bat assembleDebug
```

The file lands in `android/app/build/outputs/apk/debug/app-debug.apk`. Copy it to
a phone and open it — Android will ask permission to install from an unknown
source.

Or from inside Android Studio, which is easier to find than it looks — the menu
item people hunt for is **not** "Generate Signed Bundle":

**Build → Build Bundle(s) / APK(s) → Build APK(s)**

It builds and then puts a notification in the bottom-right corner saying *APK(s)
generated successfully* with a **locate** link in it. That link opens the folder.
If you miss the notification it is gone — the file is still at
`android/app/build/outputs/apk/debug/app-debug.apk`, and that path does not
change, so it is worth bookmarking rather than hunting for the popup.

**Release** needs signing. In Android Studio: **Build → Generate Signed Bundle /
APK → APK**, create a keystore when it asks, and keep that keystore somewhere
safe — lose it and you cannot update the app on Play later. The signed file lands
in `android/app/build/outputs/apk/release/app-release.apk`.

## Things that go wrong

- **"SDK location not found"** — open the project in Android Studio once and let
  it write `android/local.properties`, or create it yourself with
  `sdk.dir=/path/to/Android/Sdk`.
- **Gradle sync fails on a fresh install** — nearly always the missing
  *SDK Command-line Tools*. Install it and sync again.
- **The app launches but shows the old version** — you skipped `cap sync`. Use
  `npm run android` rather than pressing Run on its own.
- **A blank screen** — check `dist/index.html` exists and `webDir` in
  `capacitor.config.json` still says `dist`. `chrome://inspect` on a desktop
  Chrome will show the WebView's console for a connected device.
- **No sound** — the ambience tracks are in `dist/audio/`, and `cap sync` copies
  whatever is in `dist/`. If you cleaned `dist/` by hand, rebuild before syncing.

## The notification, and app blocking

Both are `native/focus-guard`, a Capacitor plugin that lives **in this repo**
rather than inside `android/` — `android/` is generated and git-ignored, so
anything put there is thrown away by the next `npm run cap:add:android`.
Nothing to install: it is a `file:` dependency in `package.json`, so
`npm install` links it and `npx cap sync` compiles it in.

Everything below is feature-detected on the web side (`50-guard.js`). On the
desktop app, in a browser and in the test harness there is no plugin, the menu
row for blocking hides itself, and none of it exists.

### The notification a block posts

**It appears when you leave the app and goes when you come back.** A permanent
notification for a timer you are looking at is clutter with a countdown in it.

* The countdown is **drawn by Android**, not by the app —
  `setChronometerCountDown`, which is handed an instant and ticks it down
  itself. That is the whole reason it is native: a notification the app has to
  wake up and rewrite every second is wrong the moment the app is frozen, which
  is exactly when it is the only thing you can see. The seconds keep moving with
  the process dead.
* **Stop, and Pause or Continue.** Two at a time, because a Pause button on an
  already-paused timer is a control that does nothing. They work whether or not
  the app is still alive: the press is applied to a mirror of the clock kept in
  SharedPreferences, and the web app picks it up and applies it for real the
  next time it runs.
* **The end of a block is an AlarmManager alarm**, handed over when the block
  starts. It fires whether or not the web view was ever given another
  instruction, so the end still announces itself from a pocket.

Coming back into the app **holds the clock** for a moment while the phone is
asked what happened. Pause from the notification, twenty minutes in a pocket,
open the app: without that hold the 250ms loop starts the instant the web view
thaws and writes twenty minutes that never happened into the log. See
`guardHolding()` in `50-guard.js`.

### App blocking

ScreenZen's feature set, on Android. **Menu → App blocking.** The row only
appears on the phone build.

**Rules.** A rule is a group of apps and websites with one set of settings; a
rule with one app in it is per-app settings. Each rule has:

| | |
|---|---|
| **In force** | during focus blocks, during any session, always, or on a schedule (days, and hours that may run overnight) |
| **The pause** | seconds to sit through, and optionally longer with each open today |
| **What it asks** | your own line on the screen, instead of "Take a breath." |
| **Before it opens** | nothing, say why (ten characters), or do a sum |
| **Open it for** | the choice of minutes offered — never more than is left of a daily minutes limit |
| **Quick looks** | three one-minute looks a day that are not counted as opens |
| **Limits** | opens a day and minutes a day, shared across the whole rule; at a limit, block until tomorrow or keep pausing |
| **Wait between opens** | a cooldown from when the last allowance ran out |
| **Unlock odds** | the chance the way through is offered at all; a miss keeps it shut for a minute |
| **Block outright** | no way through while the rule is in force |

The shield also lists your own open tasks as something to do instead, and says
what today has looked like for that rule. The page shows today, the last seven
days, and a streak of days inside your limits.

**Websites** are blocked by reading the address bar of Chrome, Firefox, Samsung
Internet, Edge, Brave, Opera, Vivaldi, Kiwi and DuckDuckGo, found by view id.
That is best effort: a browser update can rename the view.

**Lock.** While it is on, every change — including unlocking — waits 5 min to 4
hours before it happens, enforced on the phone as well as on the page
(`GuardRules.accept`). The Settings screens that would switch blocking off are
blocked too, and **uninstall protection** makes the app a device admin with no
powers, so it cannot be uninstalled while locked; it is removed again when the
lock comes off. Moving the phone's clock forward while locked does not reset the
daily limits. None of this is a security boundary — safe mode gets past all of
it — it is the friction ScreenZen's lock is.

**Grayscale** turns the screen black and white while a blocked app or site is in
front. Android only lets an app do that after a one-time grant, with the phone
plugged in:

    adb shell pm grant app.focussimulator.mobile android.permission.WRITE_SECURE_SETTINGS

Without it the page shows that command instead of a switch.

**Not done**, and why: accountability friends (needs server work), blocking on
Windows (a different mechanism entirely), and grayscale without the adb grant
(Android does not allow it).

**The rules are tested on the JVM**, because this machine cannot run an emulator
(no system image, and virtualization is off in firmware):

    cd android && gradlew :focus-guard:testDebugUnitTest

It needs three things from Android and the page checks all three, out loud,
because a blocker that is switched on and silently not blocking is the failure
mode of every app of this kind:

| | Why |
|---|---|
| **Notifications** | to post anything at all — a normal prompt |
| **Display over other apps** | **not for drawing.** Since Android 10 a background app may not start an activity, and holding this permission is the exemption. Without it the blocking screen never appears and nothing says so. |
| **Accessibility service** | the only way to be told, promptly, which app just came to the front. UsageStats can be asked the same question but only answers about the recent past, so you get a second or two inside the app first — which is the second or two that matters. |

**What the service reads.** The package of the window in front, always. A
browser's address bar, by view id, only while a rule blocks a website. The words
on a Settings screen, only while the lock is on, to recognise the few screens
that would turn blocking off. It stores app and site names with seconds, and
sends nothing anywhere. This used to be window-state events with no content
flags at all; website blocking cannot be done that way, so the description
Android shows before the permission is granted now says exactly the above.

**The blocklist stays on the phone.** It is the one thing you set up that does
not ride in the account: a list of package names is a list of things a laptop
does not have and a second phone has differently. See HANDOFF §7.

## Worth knowing about the phone build

- **Pressing Home does not stop the timer.** The countdown is wall-clock
  arithmetic against the end time rather than a count of ticks, so a block that
  runs with the screen off comes back with the right number on it. The running
  session and the embers it has earned are written to disk on the way out and
  brought up to date the moment you return — Android throttles background
  timers to nothing within a minute or two, so neither is left to chance.
- **The screen stays awake** during a session (the app asks for a wake lock) and
  releases it when the timer stops.
- **Effects** in the menu turns the weather off. On a mid-range phone that is the
  single biggest thing you can do for battery.
- **Focus together** works over the same connection as on desktop, so two phones
  on the same wifi can share a timer.
- **Backups** move between phone and desktop: *Menu → Your data → Export backup*
  writes a `.json` that *Import backup* reads on any copy.
